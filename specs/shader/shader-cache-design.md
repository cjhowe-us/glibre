## 1. Purpose

`ShaderCache` is the single aggregate in the `shader` context permitted
to **store and retrieve compiled shader artifacts on disk and in
memory**. Its one responsibility is **mapping a content-addressed
composite key — `(PermutationKey ⊕ source-hash ⊕ canonical-flag-hash ⊕
target)` BLAKE3-collapsed to a 32-byte `ShaderHash` — onto a sealed
`ShaderArtifact` bundle (bytecode + `ReflectionBlob` + `DescriptorLayout`
+ identity envelope)**, idempotently and immutably. It serves lookups,
absorbs idempotent inserts at cook time, drops drift-invalidated entries
in editor / dev-loop builds, and bounds its in-memory hot set under a
per-context heap ceiling. On any refusal it leaves the on-disk store
untouched and the caller's prior cached entries live.

What `ShaderCache` explicitly refuses to own:

- **Compilation.** Driving slangc, building the canonical flag list,
  emitting bytecode — `CompilationPipeline` (SPEC §4.3, spike #749).
  `ShaderCache` accepts a sealed `ShaderArtifact` and stores it; it
  never invokes a backend.
- **Source ingestion.** `.slang` reading, include-closure walking,
  `source_hash` derivation — `ShaderSource` (SPEC §4.1, spike #745).
  `ShaderCache` consumes `source_hash` as an opaque 32-byte key
  component.
- **Permutation key composition.** Axis encoding / decoding /
  enumeration — `PermutationKey` (SPEC §4.2, spike #747). `ShaderCache`
  consumes `PermutationKey::to_bytes()` as an opaque key component.
- **Reflection extraction.** Slangc native-reflection ingest, frequency
  tagging — `ReflectionBlob` (SPEC §4.4, spike #751). `ShaderCache`
  embeds the sealed `ReflectionRecord` inside `ShaderArtifactRecord`
  but never re-parses it.
- **Descriptor layout derivation.** Reflection → 4-frequency table —
  `DescriptorLayout` (SPEC §4.5, spike #753). Same posture: embedded
  by value, never re-derived inside the cache.
- **Backend selection.** Slang vs hypothetical alternative source
  language — `IShaderBackend` (SPEC §4.7, spike #757). The cache is
  backend-agnostic; `target` is a u8 enum ordinal.
- **PSO state caching.** GPU pipeline-state objects keyed by
  `(shader_hash, render-state-hash)` — `PSOCache` (specs/render/SPEC.md
  §4.1.7). `shader` SPEC §3 refusal 4. `ShaderCache` ends at
  `ShaderArtifact`; the PSO is `render`'s.
- **GPU memory, command encoders, runtime binding.** SPEC §3 refusals
  1, 4, 5.
- **File-system watching.** Source-change detection lives in the
  platform `FileWatcher` (spike #719). `ShaderCache` exposes an
  invalidation entry point the watcher (via `ShaderSource`) calls; it
  does not poll, debounce, or schedule.
- **Migration of bytecode bytes.** A schema bump on
  `ShaderArtifactRecord` migrates the envelope only; bytecode is
  **regenerated by re-running `CompilationPipeline`**, never
  transformed (SPEC §7.4 rule 5). The cache enforces this by refusing
  any migration touching the `bytecode` field.

If the composite-key composition rule, the on-disk CAS layout, the
manifest sort order, the in-memory hot-table eviction policy, the
schema-ABI gate, the integrity-check rule, or the invalidation
contract changes, this design changes. Anything else is out of scope.

Glibre-native requirements added beyond harmonius:

- **Composite key is BLAKE3-collapsed.** SPEC §2 / §4.6 invariant 1.
  A 32-byte `ShaderHash` is the sole CAS lookup key; the four input
  components are not stored as a tuple at the lookup boundary. The
  full identity (`source_hash`, `flags_hash`, `key`, `target`) is
  retained inside `ShaderArtifactRecord` for diagnostics and integrity
  checks but never participates in the lookup.
- **On-disk format is versioned and refusal-driven.** §7 below pins
  `schema_abi_hash` at cook time; loaders refuse to migrate at runtime
  (`Error::CacheIntegrity`). Re-cook is cheap; migration of bytecode
  bytes is forbidden by SPEC §7.4 rule 5.
- **Lookup miss is success, not failure.** SPEC §10 `CacheLookupMiss`
  is the *only* `Error` arm callers handle non-fatally. The §4 surface
  splits the API into `get()` (returns `nullptr` on miss; non-error)
  and `lookup()` returning `std::expected` (where `unexpected` is
  reserved for `CacheCorrupt` / `CacheIntegrity` /
  `CacheReadOnlyViolation`).
- **Hot set is bounded; cold disk is unbounded.** §9 in-memory ceiling
  is the SPEC §9.4 pool table 24 MiB row for the `shader` context.
  The cooked `ShaderLibrary` on disk has no engine-imposed size cap
  (asset-pipe budgets live outside `shader`).
- **Eviction is a 2Q-LRU.** §9.4 below selects 2Q over straight LRU to
  resist scan-heavy cold-load cooker behaviour washing out the hot
  set in editor / dev-loop builds. Shipping never evicts because
  shipping is read-only and the entire manifest fits the ceiling at
  MVP scale.

## 3. Detailed Model

### 3.1 Aggregate composition

```text
ShaderCache (root, repository-shaped)
├── std::filesystem::path             root_                    // identity
├── bool                              read_only_               // shipping = true; editor/cooker = false
├── ShaderCacheManifest               manifest_                // §7.5 sidecar, mmap'd
├── HotTable                          hot_                     // in-memory 2Q-LRU, §9.4
├── ColdLoader                        cold_                    // mmap-backed CAS reader, §3.5
├── (tooling-only) Cooker             cooker_                  // §3.6, #if !GLIBRE_SHIPPING
└── (tooling-only) IntegrityWalker    integrity_               // §3.7, #if !GLIBRE_SHIPPING

ShaderCache::Library (cooked, read-only handle, §4)
├── std::filesystem::path             library_root_
├── ShaderCacheManifest               manifest_                // independently owned; mmap'd at open
└── ColdLoader                        cold_                    // independently owned; no parent ShaderCache required
                                                               // Shipping: Library is the sole runtime object.
                                                               // Tooling: ShaderCache::cook() moves a clone of its
                                                               //   ColdLoader state into the returned Library (the
                                                               //   parent ShaderCache's cold_ is unchanged).

ShaderArtifact (value, sealed, §5 SPEC)
├── PermutationKey                    key
├── CompileTarget                     target                   // MetalLib (MVP), DXIL (post-MVP)
├── ShaderHash                        hash                     // 32-byte BLAKE3 (CAS key)
├── eastl::vector<std::byte>          bytecode                 // metallib (MVP) or DXIL bytes
├── ReflectionBlob                    reflection
└── DescriptorLayout                  descriptor_layout
```

Every field of every owned sub-object is private; the §4 surface
exposes value-equal accessors (`get`, `lookup`) and value-typed
mutators (`insert`, `invalidate`, `compact`). No member of
`ShaderCache` is reachable from outside the aggregate without going
through that surface.

### 3.2 Composite-key composition (`ShaderHash`)

The CAS lookup key is a single 32-byte `ShaderHash`. Its composition
is **spec-frozen** by SPEC §2 / §4.6 invariant 1 / §6.4 step 2d and
**not negotiable** by this design:

```text
artifact_hash := BLAKE3(
    source_hash      // 32 bytes, from ShaderSource::preprocessed().total_hash (#745)
  ‖ key.to_bytes()   // bit-stable packed PermutationKey bytes (#747; SPEC §4.2 inv 1)
  ‖ flags_hash       // 32 bytes, BLAKE3 of canonical compile-flag list from #749
  ‖ u8(target)       // CompileTarget enum ordinal: MetalLib=0, DXIL=1 (post-MVP)
)
```

The four input components are produced by upstream aggregates and
arrive at `ShaderCache::insert` already-canonicalised:

| Component       | Producer                | Bit-stability source                                                                                                |
|-----------------|-------------------------|---------------------------------------------------------------------------------------------------------------------|
| `source_hash`   | `ShaderSource` (#745)    | UTF-8, LF-normalised, BOM-stripped; BLAKE3 over normalised bytes ‖ ordered include closure (sibling design §3.7).   |
| `key.to_bytes()`| `PermutationKey` (#747)  | Mixed-radix encode in tuple-field order; reserved headroom for additive axis growth (SPEC §4.2 inv 1, §7.4 rule 1).|
| `flags_hash`    | `CompilationPipeline` (#749) | Sorted, deduped argv; BLAKE3 over the canonical flag bytes (SPEC §6.2; SPEC §4.3 inv 4 cache-key feeder).      |
| `u8(target)`    | `CompileTarget` enum (§5)| Stable enum ordinal; never reordered.                                                                               |

`ShaderCache` **does not validate** these components beyond requiring
that the in-flight `ShaderArtifact::hash` re-derives bit-equal from
the four stored fields on insert (the integrity check; §3.7). A
caller that lies about the components produces a hash that re-derives
disagreeably and is refused with `Error::CacheIntegrity`.

### 3.3 Entry record (`ShaderArtifactRecord`)

The on-disk envelope mirrors SPEC §7.2 verbatim. Two fields beyond the
key components carry the artifact body; one carries operational
diagnostics:

```text
ShaderArtifactRecord (Fory schema; §7.2 SPEC)
├── key                : PermutationKeyRecord                  // tag 1
├── target             : u8                                    // tag 2 (CompileTarget ordinal)
├── source_hash        : bytes32                               // tag 3
├── flags_hash         : bytes32                               // tag 4
├── artifact_hash      : bytes32                               // tag 5 (CAS key; §3.2)
├── bytecode           : bytes                                 // tag 6 (metallib MVP / DXIL post-MVP)
├── reflection         : ReflectionRecord                      // tag 7 (#751)
├── descriptors        : DescriptorLayoutRecord                // tag 8 (#753)
└── producer_label     : string                                // tag 9 (e.g. "slang-slangc-1.7+glibre-shadercc-0.1")
```

Operational rules:

1. **Immutable once stored.** SPEC §4.6 invariant 1. `insert` of an
   existing `artifact_hash` is a no-op; the on-disk file is never
   rewritten in place. The cooker's atomic-write step (§3.6) writes
   to `<aa>/<bb>/<hash>.tmp` and renames to `<hash>` only after a
   successful BLAKE3 self-check.
2. **No back-pointer to source path.** The record stores `source_hash`
   only; it does not embed `SourceId`. A shader removed from the
   project is detected as orphan by the cooker (manifest no longer
   references it) and garbage-collected on the next cook walk
   (§3.6 step 5b). The runtime never deletes.
3. **`producer_label` is diagnostic-only.** It is not a key component
   and does not feed `artifact_hash`. It exists so an editor /
   asset-pipe debugger can identify which build of which backend
   emitted a given blob; it is logged on `CacheCorrupt` and
   `CacheIntegrity` arms.
4. **`bytecode` is opaque to the cache.** The cache never decodes,
   re-parses, or rewrites the bytecode. Schema migrations refuse to
   touch this field (SPEC §7.4 rule 5); migrations that would require
   touching it surface as a re-cook trigger, not a transform.

### 3.4 On-disk CAS layout

Restated and refined from SPEC §7.5:

```text
<library_root>/
    manifest.fory                              # ShaderCacheManifest, §7.2 SPEC
    artifacts/<aa>/<bb>/<hash>                 # ShaderArtifactRecord blobs, BLAKE3 CAS
                                               #   <aa><bb> = first 4 hex chars of artifact_hash
                                               #   <hash>   = full 64-char hex artifact_hash
                                               # File contents = Fory-encoded ShaderArtifactRecord.
    artifacts/<aa>/<bb>/<hash>.tmp             # Cooker scratch; renamed on success.
                                               # Never present at process boundary
                                               # (atomic-write contract; §3.6 step 4).
```

CAS-layout invariants:

1. **Two-level fan-out.** `<aa>/<bb>` partitions the directory tree
   four hex digits deep, capping per-directory entry count at ~256
   subdirectories times ~256 leaf directories times ~K artifacts
   per leaf. An MVP-scale archive (~10 k artifacts) fits comfortably
   in one or two leaves per `<aa>`; an unbounded asset-pipe-scale
   archive remains within filesystem limits on APFS / ext4.
2. **No symlinks, no hard links.** Each artifact occupies exactly one
   inode under one path. Symlinks would defeat the integrity walk
   (§3.7) and break atomic-rename guarantees on case-insensitive
   filesystems (APFS default).
3. **`manifest.fory` is the single index.** Iterating the directory
   tree for a "list all artifacts" query is **not** a supported
   operation; the manifest enumerates everything reachable. Orphan
   files (CAS file not referenced by manifest) are an integrity
   violation, not a feature; the cooker garbage-collects them on the
   next cook walk (§3.6 step 5b).
4. **Atomic write at file granularity.** The cooker writes
   `<hash>.tmp` first, BLAKE3-checks the on-disk bytes against the
   target hash, then renames over `<hash>`. A crashed cooker leaves a
   `.tmp` orphan; the next cook walk deletes any `.tmp` older than
   the current run before walking artifacts. Runtime never sees a
   `.tmp` file under a non-`.tmp` path.

### 3.5 In-memory hot table (`HotTable`)

The runtime read path holds a bounded subset of artifacts memory-
resident. Architecture:

```text
HotTable (SPEC §9.4 pool table 24 MiB ceiling)
├── eastl::hash_map<ShaderHash, Entry>      index_           // O(1) lookup, BLAKE3-keyed
├── TwoQueueLRU<ShaderHash>                 lru_             // §9.4 eviction policy
├── std::atomic<u64>                        live_bytes_      // ContextTag::shader bookkeeping
└── std::shared_mutex                       mu_              // multi-reader, single-writer (§6)

Entry
├── ShaderArtifact         artifact            // owned copy, decoded from CAS
└── std::atomic<u32>       refcount            // borrowed by render-side PSO build; never freed while > 0
```

Hot-table rules:

1. **Lookup is O(1).** The `eastl::hash_map<ShaderHash, Entry>` is
   keyed on the full 32-byte `ShaderHash`; collisions are
   astronomically unlikely under BLAKE3 (256-bit) but the integrity
   check on insert (§3.7) detects any that nonetheless arise.
2. **Decoding is lazy at the warm boundary.** A `lookup` on a hash
   not in `index_` walks the cold path (§3.5.1 below): the manifest
   binary search resolves the CAS file path, the file is mmap'd, the
   `ShaderArtifactRecord` is Fory-decoded, the resulting
   `ShaderArtifact` is moved into a fresh `Entry`, and the entry is
   admitted into `index_` and `lru_`. Subsequent lookups hit the hot
   table.
3. **Eviction is 2Q-LRU.** A scanning workload (cooker iterating
   every artifact for a project-pruned cook) does not wash out the
   hot set; recently-promoted entries stay resident. Eviction
   triggers when `live_bytes_ + incoming_size > 24 MiB` (SPEC §9.4
   pool table ceiling; see §9.2); a victim's `refcount` of 0 is
   required (live PSOs hold borrows; eviction waits for the borrow
   to drop in editor / dev-loop, and refuses with
   `Error::OutOfBudget` only under `GLIBRE_ALLOC_STRICT=1`).
4. **Eviction never deletes from disk.** `evict(hash)` drops the
   entry from `index_` and `lru_` only; the on-disk CAS file is
   untouched. Re-lookup after eviction walks the cold path and
   re-admits.
5. **Shipping never evicts.** SPEC §9.5 declares the cooked
   `ShaderLibrary` rehydration cost is paid before frame 1; in
   shipping the entire MVP-scale manifest fits the 24 MiB hot-set
   ceiling (SPEC §9.4 pool table). The 2Q-LRU code path is linked in
   shipping but the `evict` call site is unreachable at MVP scale.
   A future post-MVP archive that exceeds the ceiling reverts to the
   2Q steady-state.

#### 3.5.1 Cold path (CAS read)

```text
cold_lookup(hash) :
    1. entry := manifest_.binary_search_by_artifact_hash(hash)
       // SPEC §6.4 read step 2a; manifest entries sorted ascending.
    2. if !entry: return nullptr            // miss; not an error (§4)
    3. path := root_ / "artifacts" / hash[0:2] / hash[2:4] / hash
    4. mapping := mmap(path, MAP_PRIVATE)
       // Transient MAP_PRIVATE mmap; used only for Fory decode.
       // The mmap is NOT kept for the artifact's lifetime; it is a
       // decode scratch window, not a zero-copy residence.
    5. record := fory_decode<ShaderArtifactRecord>(mapping.bytes)
       // data middleman dylib (#732 fory-codegen) handles decode.
       // Decode copies all variable-length fields (bytecode, reflection,
       // descriptor layout) into shader-heap allocations tagged
       // ContextTag::shader. After this step the artifact's bytes live
       // exclusively in the shader heap, counted against the 24 MiB
       // HotTable ceiling (§9.2 "Decoded ShaderArtifact bodies ~23 MiB").
    6. if record.artifact_hash != hash:
           return std::unexpected{Error::CacheCorrupt}
    7. artifact := ShaderArtifact::from_record(record)
       // Moves heap-owned fields; record's mmap-backed storage is no
       // longer referenced after this point.
    8. munmap(mapping)
       // Release the transient decode window. The artifact's bytes are
       // now fully owned in the shader heap; the kernel page-cache
       // backing the CAS file may or may not remain warm (irrelevant —
       // subsequent reads go through the HotTable, not disk).
    9. return artifact
```

The cold path is exercised exactly once per `(ShaderHash, process)`
in steady state; subsequent lookups hit the hot table.

### 3.6 Cooker (write path; tooling-only)

The cooker is the **sole writer** to `ShaderCache`; it runs strictly
offline behind `#if !GLIBRE_SHIPPING` (SPEC §6.5; §4.6 inv 2). Restated
and refined from SPEC §6.4:

```text
cook(span<const PermutationKey> enumerated_keys) :
    1. enumerated_keys = permutation/enumeration_table.walk(project_pruner)
       // SPEC §6.4 step 1; #747 produces this set.

    2. tmp_dir := root_ / "artifacts" / ".cook-<run_id>"
       // Ephemeral scratch for this cook run.

    3. for each key k in enumerated_keys:
       3a. for each (CompileTarget t) in {MetalLib}:    // MVP; DXIL post-MVP
           3b. source_hash := ShaderSource::preprocessed().total_hash      // #745
           3c. flags_hash  := BLAKE3(canonical_flags(k, t))                // #749
           3d. artifact_hash := BLAKE3(source_hash || k.to_bytes() ||
                                       flags_hash || u8(t))
           3e. if cas_store.has(artifact_hash):
                   continue              // idempotent; SPEC §4.6 inv 1
           3f. artifact := IShaderBackend::compile(source, k, t)           // #749
           3g. artifact.reflection := IShaderBackend::reflect(artifact)    // #751
           3h. artifact.descriptor_layout := DescriptorLayout::derive(
                                                 artifact.reflection)     // #753
           3i. record := ShaderArtifactRecord{
                   key, target=t, source_hash, flags_hash,
                   artifact_hash, bytecode=artifact.bytecode,
                   reflection=artifact.reflection,
                   descriptors=artifact.descriptor_layout,
                   producer_label=backend.label(),
               }
           3j. tmp_path := tmp_dir / hex(artifact_hash) + ".tmp"
           3k. atomic_write_with_self_check(tmp_path, fory_encode(record), artifact_hash)
           3l. mkdir_p(root_ / "artifacts" / hex_prefix(artifact_hash))
           3m. rename(tmp_path, root_ / "artifacts" / .. / hex(artifact_hash))

    4. manifest := ShaderCacheManifest{
           cache_root_relative: <relative path>,
           schema_abi_hash:     glibre_types_abi_hash(),                  // §7.4
           entries:             sort_ascending(by artifact_hash, walk_cas()),
           enumerated_keys:     sort_ascending(by k.to_bytes(), enumerated_keys),
       }

    5. integrity_walker:
       5a. for each manifest entry: assert CAS file present, BLAKE3 self-check passes.
       5b. for each CAS file: assert manifest entry present.
                              // Orphans (file not referenced) are deleted in editor /
                              // dev-loop cooks; flagged Error::CacheIntegrity in
                              // a strict cook (--strict).
       5c. either failure → Error::CacheIntegrity (SPEC §4.6 inv 3, §10).

    6. atomic_write(<library_root>/manifest.fory, fory_encode(manifest))

    7. rmdir(tmp_dir)            // unconditional cleanup; .tmp orphans are absent
                                  // by construction at this point.
```

Cooker invariants:

1. **Idempotent at every step.** Step 3e short-circuits already-stored
   keys; step 5b's GC is idempotent across runs; step 6 rewrites the
   manifest unconditionally because it is a derived index.
2. **Atomic at file granularity.** Steps 3k–3m and 6 each obey the
   atomic-write rule (§3.4 invariant 4). A killed cooker leaves at
   most one `.tmp` orphan; the next cook deletes it in step 7's
   moral equivalent (a startup pass over `tmp_dir` siblings).
3. **Single-writer.** Only one cooker process may operate against a
   given `<library_root>` at a time. Concurrency is enforced by an
   advisory `flock(2)` on `<library_root>/.cook.lock`; a second
   cooker that fails to acquire the lock refuses with
   `Error::CacheReadOnlyViolation` (which is a category abuse —
   `CacheReadOnlyViolation` semantically covers the shipping
   read-only-flag case, not a writer-lock-busy case; the structured
   log carries `detail="writer_lock_busy"` to disambiguate at
   runtime). A dedicated `Error::CacheLockContention` arm should be
   introduced in the follow-up implementation plan that lifts §12
   spike findings into SPEC §10 text; that plan must add the new
   arm to the `shader::Error` closed enum before
   `ShaderCache::cook` implementation lands.
4. **No partial publishes.** `manifest.fory` is rewritten only after
   every step 3 entry has been atomically renamed into place. A
   reader concurrent with a cooker (editor + watcher loop) sees
   either the prior manifest (with its prior entry set) or the new
   manifest (with the new entry set) — never a half-published view.

### 3.7 Integrity walker

A standalone routine, callable from the cooker (step 5) and from a
diagnostic CLI (`glibre-shadercc verify <library_root>`). Two checks:

1. **Manifest → CAS coverage.** Every `ShaderManifestEntry` references
   a CAS file present at the derived path. Absent ⇒ `Error::CacheCorrupt`
   (the cooker re-runs to repopulate; runtime treats the entry as a
   miss and surfaces `CacheLookupMiss`).
2. **CAS → manifest coverage.** Every CAS file under `artifacts/`
   has a manifest entry pointing at it. Absent ⇒ orphan blob;
   `Error::CacheIntegrity` in strict cooks, silent GC in dev-loop
   cooks (the orphan is deleted).

The walker also re-derives `BLAKE3(record bytes)` and asserts the
result equals the file's path-hash. A mismatch is `Error::CacheCorrupt`
and is logged with `producer_label` so the offending build can be
traced.

### 3.8 Compaction

Compaction is **not garbage collection** — orphan deletion is the
cooker's job (§3.6 step 5b). Compaction is the **on-disk reorder /
pack** operation invoked when a project's archive grows beyond the
bound where the two-level fan-out becomes uneven (e.g., a single
`<aa>/<bb>` directory exceeds 16 k entries). The compactor:

1. Walks the manifest in `artifact_hash`-ascending order.
2. Re-emits the CAS files into a fresh `<library_root>.compacted/`
   directory tree (same layout; same file contents; potentially
   different filesystem block ordering for sequential read locality).
3. Re-emits the manifest pointing at the new tree.
4. Atomically swaps the two roots (`rename(<library_root>,
   <library_root>.old)` then `rename(<library_root>.compacted,
   <library_root>)`); a recovery from a crash mid-swap detects the
   `.old` and either rolls back (`.compacted` absent) or rolls forward
   (`.compacted` present; `<library_root>` absent).

Compaction is a tooling-only operation; it does not run in shipping.
It is offered as a cooker subcommand (`glibre-shadercc compact`) and
is **not** an automatic policy; an asset-pipe operator decides when
to invoke it.

## 4. Public Surface

The §5 surface in `specs/shader/SPEC.md` is authoritative. This
section restates the subset owned by `ShaderCache` with per-method
behaviour annotations and pre-/post-conditions, and it adds the two
private-but-cross-aggregate entry points (`invalidate`, `compact`)
that SPEC §4.6 implies but does not declare in §5.

### 4.1 Types (locked from SPEC §5)

```cpp
namespace glibre::shader {

// Strong alias distinguishing source-content hashes from artifact hashes.
// Both are 32-byte BLAKE3 digests, but they carry different semantic roles:
//   ShaderHash        — the composite CAS lookup key (§3.2; source_hash ‖ key ‖
//                       flags_hash ‖ target, BLAKE3-collapsed). Identifies a
//                       compiled artifact.
//   SourceContentHash — the preprocessed source digest produced by ShaderSource
//                       (#745 §3.7). Identifies a Slang translation unit's
//                       content. Used as one *input component* of ShaderHash and
//                       as the invalidation key in invalidate_by_source_hash.
// Never pass a ShaderHash where a SourceContentHash is expected or vice versa;
// the types are distinct to make this impossible at compile time.
struct SourceContentHash {
    eastl::array<std::byte, 32> bytes{};
    [[nodiscard]] bool operator==(const SourceContentHash&) const noexcept = default;
};

class ShaderCache {
public:
    static std::expected<ShaderCache, Error>
    open(const std::filesystem::path& cache_root, bool read_only);

    // Lookup, fast path. Returns a non-owning pointer into the hot
    // table; nullptr on miss. Miss is NOT an error (SPEC §10
    // CacheLookupMiss = success-in-disguise; see §4.2 below).
    const ShaderArtifact* get(const ShaderHash&) const noexcept;

    // Lookup, structured path. unexpected() arms reserved for
    // CacheCorrupt / CacheIntegrity / CacheReadOnlyViolation only;
    // the success arm is std::optional<ShaderArtifact> (engaged on
    // hit, disengaged on miss). Used by the cooker / editor to
    // distinguish miss from corruption.
    std::expected<std::optional<ShaderArtifact>, Error>
    lookup(const ShaderHash&) const noexcept;

    // Idempotent insert. Tooling-only in shipping link target;
    // shipping read_only_=true rejects with
    // Error::CacheReadOnlyViolation (SPEC §10).
    std::expected<void, Error> insert(ShaderArtifact);

    // Cooked, read-only shipping handle.
    class Library;
    std::expected<Library, Error>
    cook(eastl::span<const PermutationKey> enumerated) const;

    // Editor / dev-loop only: drop hot-table entries whose embedded
    // source_hash matches `affected_source_hash`. The parameter is a
    // SourceContentHash (the preprocessed source digest from
    // ShaderSource #745), NOT a ShaderHash — the two 32-byte roles
    // are semantically distinct (see SourceContentHash above).
    // Returns the set of ShaderHashes evicted (used by the SPEC §8.5
    // publisher to drive render's PSO invalidation). On-disk CAS
    // untouched; cooker is the sole disk writer.
    eastl::vector<ShaderHash>
    invalidate_by_source_hash(const SourceContentHash& affected_source_hash) noexcept;

    // Tooling-only on-disk reorder; see §3.8. Offline subcommand.
    std::expected<void, Error>
    compact() const;

private:
    ShaderCache() = default;
    std::filesystem::path root_{};
    bool                  read_only_{true};
    // (HotTable, ColdLoader, ShaderCacheManifest fields — §3.1)
};

class ShaderCache::Library {
public:
    // Shipping-path factory. Opens a cooked ShaderLibrary archive at
    // `library_root` in read-only mode. Validates `manifest.fory`'s
    // `schema_abi_hash` against the host's `glibre_types_abi_hash()`
    // and returns a fully-initialised read-only Library; no parent
    // ShaderCache is required.
    //
    // Pre-conditions: `library_root` exists, contains `manifest.fory`.
    // Failure modes: CacheCorrupt (manifest decode failure),
    //                CacheIntegrity (schema_abi_hash mismatch).
    //
    // This is the sole factory the shipping runtime calls. cook() is
    // tooling-only and unavailable in GLIBRE_SHIPPING builds.
    static std::expected<Library, Error>
    open(const std::filesystem::path& library_root);

    const ShaderArtifact* get(const ShaderHash&) const noexcept;

private:
    Library() = default;
    friend class ShaderCache;
};

}  // namespace glibre::shader
```

The `lookup` and `invalidate_by_source_hash` entry points refine SPEC
§5: they are *implied* by §4.6 ("provides idempotent put/get and the
cooked `ShaderLibrary` archive layout"), §8.2 invariant 5
("publishes the affected `ShaderHash` set"), and §10's distinction
between `CacheLookupMiss` (fallback) and `CacheCorrupt`
(fatal). Spike #755 declares them; the §5 amendment lands in the
follow-up plan that lifts spike findings into SPEC text.

### 4.2 Surface rules

- **`std::expected<T, shader::Error>` at every fallible boundary.**
  Per `reviews/decisions/error-model.md`. `shader::Error` is a closed
  enum (SPEC §5); it composes into engine-wide `glibre::Error` at the
  cross-context seam, not inside `ShaderCache`.
- **No exceptions cross the public surface.** The aggregate compiles
  with `-fno-exceptions` (per error-model.md). Internal use of
  `std::filesystem` / `mmap` operations that may throw are wrapped at
  first ingress and translated to `Error`.
- **No exceptions cross the plugin ABI.** The `IShaderBackend` trait
  (SPEC §4.7) is the only `shader`-context surface that crosses a
  plugin boundary; `ShaderCache` itself is `shader`-plugin-internal.
  Cross-plugin consumers (`render`'s PSO build path) reach
  `ShaderCache` by handle through middleman `data` types
  (`reviews/decisions/plugin-abi.md`).
- **Borrow rules.** `get()` / `Library::get()` return non-owning
  pointers valid for the lifetime of the returning `ShaderCache` /
  `Library`. A consumer that needs stable storage copies the
  contents. The hot-table's per-entry `refcount` (§3.5) is bumped on
  borrow and dropped on borrow release.
- **Lookup-miss is not an error.** `get` returns `nullptr`; `lookup`
  returns `std::optional` disengaged. The `unexpected` arm is
  reserved for `CacheCorrupt` / `CacheIntegrity` /
  `CacheReadOnlyViolation` (the three `fatal` cache arms in SPEC
  §10.2).
- **`ShaderCache::Library` owns its state independently.** A `Library`
  obtained via `Library::open(path)` (shipping) or `ShaderCache::cook()`
  (tooling) is a self-contained, standalone object. It owns its
  `ColdLoader` and mmap'd manifest by value — it does not borrow from,
  nor must it outlive, any `ShaderCache` instance. In shipping the
  `Library` is the *only* runtime object; no parent `ShaderCache` is
  created or required. In the editor / cooker path, `ShaderCache::cook()`
  clones the relevant ColdLoader state into the returned `Library`; the
  parent `ShaderCache`'s `cold_` member is unchanged and the two objects
  have independent lifetimes thereafter.

### 4.3 Per-method contracts

- **`open(cache_root, read_only)`** — opens the manifest sidecar,
  validates `schema_abi_hash` against the host's
  `glibre_types_abi_hash()`, and returns a `ShaderCache` whose hot
  table is empty. Pre-conditions: `cache_root` exists and contains a
  `manifest.fory` file. On `read_only=false`, the directory must be
  writable. Failure modes: `CacheCorrupt` (manifest decode failed),
  `CacheIntegrity` (`schema_abi_hash` mismatch).
- **`get(hash) const`** — single hot-table probe; fall-through to
  cold load if absent. Returns `nullptr` on miss. Wall-time bound: §9.
- **`lookup(hash) const`** — same as `get` but distinguishes miss
  (`std::optional` disengaged) from corruption (`unexpected`). Used
  by editor / cooker code that needs to surface diagnostics; not
  used on the hot path.
- **`insert(artifact)`** — tooling-only writer; see §3.6. Pre-condition:
  `read_only_` is `false`. Fails with `CacheReadOnlyViolation` in
  shipping (link-excluded, but the symbol survives so a stray test
  harness gets a deterministic refusal). Idempotent on re-insert of
  an existing hash.
- **`cook(enumerated) const`** — runs the §3.6 cooker against the
  given permutation enumeration. Tooling-only. Returns a `Library`
  handle (the cooked sidecar manifest reader); the `ShaderCache`
  itself is unchanged on success (its hot table is unmodified; the
  cooked archive is a separate read root the cooker hands off).
- **`invalidate_by_source_hash(affected_source_hash: SourceContentHash) noexcept`** —
  editor / dev-loop only. The parameter is a `SourceContentHash`
  (not a `ShaderHash`; see §4.1 type commentary). Drops hot-table
  entries whose embedded `source_hash` field matches the given
  digest; returns the affected `ShaderHash` set for the SPEC §8.5
  publisher. On-disk CAS is untouched. No-op in shipping (the
  function is link-included but unreachable; runtime has no
  source-edit trigger).
- **`compact() const`** — tooling-only on-disk reorder; see §3.8.
- **`Library::open(library_root) [static]`** — shipping-path factory.
  Opens a cooked `ShaderLibrary` archive in read-only mode without
  requiring (or constructing) a parent `ShaderCache`. Validates
  `manifest.fory`'s `schema_abi_hash` against the host's
  `glibre_types_abi_hash()` and returns a fully-initialised `Library`.
  Pre-conditions: `library_root` exists and contains `manifest.fory`.
  Failure modes: `CacheCorrupt` (manifest decode failure),
  `CacheIntegrity` (`schema_abi_hash` mismatch). This is the one
  factory the shipping runtime uses; `ShaderCache::cook()` is
  unavailable in `GLIBRE_SHIPPING` builds and must not be called from
  shipping paths.

### 4.4 Public ABI surface

`ShaderCache` is a `shader`-plugin-internal aggregate. There is no
`extern "C"` boundary — `IShaderBackend` implementations call
`ShaderCache::get` / `insert` directly (in-process). Consumers in
other plugins (`render`'s `PSOCache`) reach the cache by:

1. Receiving a `ShaderHash` through a middleman `data` event
   (`glibre::types::shader::ShaderArtifactReplaced`, SPEC §8.5).
2. Calling into the `shader` plugin through a middleman handle that
   exposes `get(ShaderHash) → const ShaderArtifact*` after
   marshalling through `data`-context POD types
   (`reviews/decisions/plugin-abi.md`).

The shipping cut (SPEC §6.5) excludes `cache/cooker.cpp` and
`cache/integrity.cpp`; in shipping, `ShaderCache::insert`,
`ShaderCache::cook`, `ShaderCache::invalidate_by_source_hash`, and
`ShaderCache::compact` are link-included as symbols (so the type
remains ABI-stable across editor / shipping) but their TUs are empty
stubs that return `Error::CacheReadOnlyViolation`. The runtime calls
only `open` and `get`.

## 5. Hot / Cold Path Split

`ShaderCache` runs on three paths with three distinct frequencies and
three distinct budgets:

| Path           | Trigger                                                      | Frequency                          | Budget                                            |
|----------------|--------------------------------------------------------------|------------------------------------|---------------------------------------------------|
| Hot (lookup)   | `render` PSO build asks for `ShaderCache::get`                | Per cold PSO build / level-stream  | **~5 µs / lookup; 0 ms / frame steady-state** (§9.3 SPEC) |
| Warm (decode)  | First `get` for a hash not yet in `HotTable`                 | First miss per process per hash    | <1 ms (manifest binary search + mmap + Fory decode) |
| Cold (insert)  | Cooker `insert`                                              | Once per `(key, target)` per cook   | Bounded by §3.6 cooker step 3 (compile-bounded)   |

The hot path is steady-state; the warm path is a one-shot per
`(ShaderHash, process)`; the cold path is offline-only.

The SPEC §9.1 `shader / 0.00 ms / frame` cell holds because:

- **Hot path is borrowed by `render`'s PSO miss path.** The §9.3 SPEC
  table's `~0.005 ms per lookup; 0 ms on PSOCache hit` cost is charged
  against the *render* CPU-submit budget when a PSO miss bubbles into
  a `ShaderCache::get`. `shader`'s own per-frame contribution is
  zero.
- **Warm path is amortised at level-stream boundaries.** PSO miss
  cascades during a level transition pay the warm cost once per
  newly-resident hash; the steady frame after the transition is
  hot-only.
- **Cold path is shipping-excluded.** `cache/cooker.cpp` is gated by
  `#if !GLIBRE_SHIPPING`; the runtime cannot reach it. The shipping
  `shader.dylib` contains only the read path (§6.5 SPEC).

## 6. Concurrency

`ShaderCache` operates under three concurrency profiles, one per
build configuration:

### 6.1 Shipping: single-writer-absent, multi-reader

`read_only_=true` in shipping. The hot table's `std::shared_mutex
mu_` is acquired in shared mode by every `get`; no `unique_lock` is
ever taken because there is no writer. Hot-table admission (the warm
path) is the one exception: after the cold load, a single thread
upgrades to a unique lock to insert into `index_` and `lru_`.
Warm-path admission is serialised at the unique-lock boundary;
multi-reader steady-state is contention-free beyond the atomic
`live_bytes_` counter.

Reader rules:

1. **No locks on `get` once the hash is in `index_`.** The hash-map
   probe is wait-free under shared lock; the `Entry::refcount` bump
   is a single `std::memory_order_acquire` increment.
2. **Borrow lifetime is bounded by the caller.** A `render`-side PSO
   build holds the borrow for the duration of the build; on
   completion the borrow is released and `refcount` drops.
3. **Eviction is unreachable in shipping at MVP scale.** §3.5 rule 5;
   the entire MVP cooked archive fits the 24 MiB hot-set ceiling.
   The `evict` code path is linked but the call site is unreachable.

### 6.2 Editor / dev-loop: MRSW (multi-reader, single-writer)

`read_only_=false` is admitted only in editor / cooker / dev-loop
builds. This is a multi-reader / single-writer (MRSW) profile —
many concurrent `get` readers coexist with at most one cooker writer
at a time (not SPSC, which implies a single consumer; here readers
are unbounded). Writers and readers coexist:

- **One writer at a time.** The cooker's advisory file lock (§3.6
  invariant 3) ensures at most one process has `read_only_=false`
  for a given `<library_root>`. Within that process, a single
  cooker thread holds the in-process writer role; concurrent cooker
  threads serialise on a `std::mutex writer_mu_`.
- **Readers see the prior manifest until the new manifest is
  committed.** Step 6 of §3.6 atomically rewrites `manifest.fory`;
  readers that opened the old manifest continue to use their mmap'd
  view (the inode survives the rename). New readers (subsequent
  `ShaderCache::open` calls) see the new manifest.
- **In-process readers under the same `ShaderCache` see RCU
  semantics.** The hot table's index admits new entries via
  unique-lock; a `get` mid-admission sees either the prior state or
  the post-admission state, never a partial entry. The
  `eastl::hash_map` is rebuilt by the writer if the manifest sidecar
  is reloaded mid-process (rare; only on explicit `reload()` from a
  test harness, not currently exposed in §4).

The choice of `std::shared_mutex` over a custom RCU is deliberate:
the writer is rare (once per cook), the reader-side cost of a
shared-lock acquire on M1 is ~3–5 ns (well inside the §9.3 5 µs
budget), and a custom RCU's complexity does not pay for itself at
this contention level.

### 6.3 `invalidate_by_source_hash` is single-threaded

The editor's filesystem watcher (#719) is single-consumer; it
serialises source-edit events. `invalidate_by_source_hash` runs on
the watcher thread under a unique lock on `mu_`, drops the affected
entries from `index_` and `lru_`, returns the affected hash set, and
releases the lock before publishing the SPEC §8.5 event. Concurrent
`get` calls during invalidation either:

- See the entry pre-invalidation and return the prior `ShaderArtifact`
  (the borrow holds; eviction blocks until `refcount` drops); or
- See the entry post-invalidation and miss to the cold path (which
  in turn re-derives the new `ShaderHash` for the affected key — but
  the cold path's manifest binary search returns the *new* manifest
  entry only after the cooker has committed step 6, which is
  upstream of the watcher's invalidation publish).

There is no half-invalidated view; the operation is serialised with
respect to `get`.

### 6.4 Re-entrancy

`ShaderCache::get` is re-entrant within a single thread. A test
harness that mocks the cold loader and recursively triggers another
`get` from inside a Fory-decode callback is admitted; the only
constraint is that each `get` invocation owns its own
`std::shared_lock` (no cross-invocation lock aliasing). `insert` is
**not** re-entrant; a writer that reentrantly inserts deadlocks on
its own unique lock and is treated as a cooker bug.

## 7. Persistence + ABI

### 7.1 On-disk format is versioned at cook time

The persistent records owned by `ShaderCache` are:

- `ShaderArtifactRecord` — one CAS blob per `(PermutationKey,
  source_hash, target)` (SPEC §7.1).
- `ShaderCacheManifest` — sidecar enumerating reachable artifacts
  (SPEC §7.1).

Both records carry Fory `version` / `since` annotations (SPEC §7.2).
The manifest additionally embeds `schema_abi_hash` — the value
`glibre_types_abi_hash()` returned at cook time (SPEC §7.3 rule 4).

`ShaderCache::open` validates the manifest's `schema_abi_hash`
against the host's:

```cpp
if (manifest_.schema_abi_hash != glibre_types_abi_hash()) {
    return std::unexpected{Error::CacheIntegrity};
}
```

The loader **does not migrate** the cache at runtime; SPEC §7.4 rule
4 makes the manifest "rebuildable, not migrated". A hash mismatch is
a build-system bug: the cooked archive lags the host's middleman
ABI. The fix is to re-cook (cheap, by construction; SPEC §3 collapse
4 / §4.6 invariant 1 say bytecode is content-addressed, and the
cooker idempotently re-walks the resolved permutation set). This is
the §1 "no migration of bytecode bytes" rule expressed as an ABI
guarantee.

### 7.2 Format-version mismatch is `CacheIntegrity`

Three flavours of mismatch all collapse onto `Error::CacheIntegrity`:

1. **`schema_abi_hash` mismatch.** The middleman ABI changed between
   cook and load; the records' field tags / wire layout may not match
   the host's expectation.
2. **`ShaderArtifactRecord.version` outside the supported range.** The
   record was written by a cooker newer (or older) than the host's
   reader's accepted version range. Migration is *technically* a
   `data`-middleman concern (#732 fory-codegen migration dispatcher)
   but for `ShaderArtifactRecord` the §7.4 SPEC rule 5 forbids
   migrating the bytecode bytes; the dispatcher returns the
   `CacheIntegrity` upstream of any envelope-only migration that would
   otherwise succeed.
3. **`ShaderCacheManifest.version` outside supported range.** Same as
   above; the manifest is a derived index and the cooker re-emits it
   on every cook, so the supported range is always exactly the cooked
   range plus one (the in-flight bump).

The §7.4 rule 4 "manifest is rebuildable, not migrated" implementation
is the loader's refusal: detect the mismatch, refuse `open`, surface
`CacheIntegrity`. Editor / dev-loop reacts by invoking the cooker;
shipping reacts by aborting (the cooked archive shipped with the
binary should match by construction).

### 7.3 Plugin-ABI surface

`ShaderCache` does not cross the plugin ABI boundary. Cross-plugin
consumers reach the cache only via:

- The middleman `data` event `ShaderArtifactReplaced` (SPEC §8.5;
  POD types, `data` middleman dylib).
- The `IShaderBackend` trait surface (SPEC §4.7), which is the
  `shader` plugin's only `extern "C"` export. Backends consume
  `ShaderCache` by handle, not by C-ABI value.

The `data` middleman dylib (#728) owns the wire layout of every
`shader`-context POD type that crosses a plugin boundary; SPEC §7.2
schemas live there. `ShaderCache` is a `shader`-plugin-internal
type and **never** crosses an ABI boundary as a value.

Plugin-ABI hash composition (`reviews/decisions/plugin-abi.md`
ABI Hash Function) covers the `IShaderBackend` trait and the
middleman POD types; it does not cover `ShaderCache` directly. A
change to `ShaderCache`'s in-memory layout is a `shader` plugin
internal change and triggers a `shader` plugin SONAME bump, which
the loader's `hot-reload-protocol.md` step 3 handles for us.

### 7.4 Cooked `ShaderLibrary` is the shipping projection

The shipping read path opens a `ShaderCache::Library` rather than a
full `ShaderCache`. SPEC §7.5 layout, recapped:

```text
<library_root>/
    manifest.fory                      # ShaderCacheManifest, mmap'd at Library::open and kept resident
    artifacts/<aa>/<bb>/<hash>         # ShaderArtifactRecord blobs, accessed on first lookup (cold path)
```

**Memory model for artifact blobs (copy-to-heap, not zero-copy mmap).**
When a `ShaderHash` is first requested via `Library::get` (or
`ShaderCache::get`) and is not yet in the hot table, the cold path
(§3.5.1) opens a transient `MAP_PRIVATE` mmap on the CAS file,
Fory-decodes the `ShaderArtifactRecord` into shader-heap allocations
(tagged `ContextTag::shader`), and immediately unmaps the file. The
decoded `ShaderArtifact` bytes live in the HotTable's shader-heap
pool and are counted against the 24 MiB ceiling (§9.2). The CAS
file's kernel page-cache backing may remain warm for OS-side readahead
benefit, but the engine does not rely on it and does not count it.
The manifest (`manifest.fory`), by contrast, is mmap'd once at open
and kept resident for the lifetime of the `Library` / `ShaderCache`
(it is a small index structure and is accessed frequently for binary
search; its pages are kernel-pager-tracked and not counted against the
24 MiB ceiling per §9.2 Allocator Rule §4).

Read-only at runtime in shipping (SPEC §4.8 invariant 3); the cooker
is the sole writer; orphan blobs and dangling references both fail
integrity verification with `Error::CacheIntegrity` (SPEC §4.6
invariant 3).

The `Library::get` symbol is the one the `render` plugin's PSO build
path resolves through; it is the sole runtime read path in shipping.

## 8. Hot-Reload Integration

The §8 SPEC contract defines the cross-context flow; this section
pins `ShaderCache`'s side of it.

### 8.1 Trigger

Source-hash drift, observed by `ShaderSource` re-ingestion (#745
sibling design §8). The watcher (#719) calls
`ShaderSource::open` on a modified `.slang`; if
`new_total_hash != prior_total_hash`, the watcher computes the
affected permutation set (SPEC §8.1) and invokes the cooker for
each `(PermutationKey, target)` pair. The cooker calls
`ShaderCache::insert` for each new artifact; on success it asks
`ShaderCache::invalidate_by_source_hash(prior_source_hash)` to drop
the now-stale hot-table entries.

Trigger rules:

1. **Cache invalidation is downstream of cooker success.** The
   watcher does not invalidate optimistically; the prior cache state
   remains live until the new artifacts are durably on disk and the
   manifest has been atomically swapped.
2. **Invalidation is keyed on `source_hash`, not `ShaderHash`.** The
   editor knows which `.slang` changed; it knows the prior
   `total_hash` (`ShaderSource` exposes it). It does not need to
   enumerate the affected `ShaderHash` set up front — the
   `invalidate_by_source_hash` walker does that (it scans
   `index_` and matches on `Entry::artifact.embedded_source_hash`).
3. **Single trigger.** Only source-hash drift fires the path. A
   plugin reload (`shader.dylib` swap) goes through the engine-wide
   `hot-reload-protocol.md` and does not call
   `invalidate_by_source_hash`; the `shader` plugin's loader-state
   migration re-opens the cache against the same `<library_root>` and
   the hot table is rebuilt from cold on demand.

### 8.2 Refresh path

The cache's contribution to a source-edit hot reload:

```text
on source_edit(source_id):
    1. ShaderSource::open(source_id) → new_preprocessed
       // #745; produces new_total_hash.
    2. if new_total_hash == prior_total_hash: return  // no-op.
    3. affected := enumeration_table.affected_keys(source_id)
       // #747; SPEC §8.1.
    4. for each (k, t) in affected × {MetalLib}:
       4a. cooker.insert(compile(source, k, t))     // §3.6 step 3
    5. evicted := cache.invalidate_by_source_hash(prior_source_hash)
    6. publish ShaderArtifactReplaced{
           source_id,
           affected_old_hashes: evicted,
           affected_new_hashes: [BLAKE3(new_source_hash || k.to_bytes() ||
                                        flags_hash || u8(t)) for ...],
           affected_permutations: affected,
           target: t,
       }
       // SPEC §8.5; render reacts.
```

Step 5's `invalidate_by_source_hash` is the only entry point this
design adds to the §8 SPEC flow. It returns the evicted set so step
6 can populate `affected_old_hashes` deterministically.

### 8.3 What survives the swap

Restated from SPEC §8.2:

1. **Hot-table entries for unaffected permutations survive verbatim.**
   `invalidate_by_source_hash` walks `index_` and only matches entries
   whose `source_hash` is the prior source's hash; everything else is
   untouched.
2. **Hot-table entries for affected permutations are dropped.** The
   on-disk CAS file remains (the prior artifact stays as an
   unreferenced blob until the next cook walk; `cooker.step 5b`
   garbage-collects on the dev-loop tier and flags it on the strict
   tier). The hot table's reference is the only one the runtime
   holds; dropping it does not free the on-disk bytes.
3. **The manifest is rewritten by the cooker.** `ShaderCache::open`
   does not re-read the manifest mid-process; the in-process
   `ShaderCache` keeps using its open mmap of the prior manifest. New
   processes (or an explicit `reopen`, which is not exposed in §4)
   see the new manifest. Editor builds typically restart the cache
   only on engine-wide hot reload, not on per-edit hot reload — the
   in-process invalidate path is sufficient for the dev loop.
4. **`PSOCache` survival is `render`'s job.** SPEC §8.2 invariant 5;
   not in this design.

### 8.4 Refusal cases

Source-edit refusals at the `ShaderCache` boundary (SPEC §8.4):

1. **Cooker insert refuses.** Any §3.6 step 3 / step 5 failure
   surfaces as `Error::CacheIntegrity` or a step-3-specific compile
   refusal (`CompilerInvocationFailed`, `CompilerExitNonZero`,
   `CompilerTimedOut`, `MetalLibEmitFailed`,
   `ReflectionExtractionFailed`, etc., all per SPEC §10.2). The
   in-flight artifact is dropped; the prior CAS entry remains the
   live entry; `invalidate_by_source_hash` is **not** called;
   `ShaderArtifactReplaced` is **not** published.
2. **`schema_abi_hash` skew during a dev-loop reload.** Should not
   occur in a dev-loop session (the host's middleman ABI is fixed
   for the process). If it does (e.g., a hot-reload of the `data`
   middleman during a session), `ShaderCache::open` would refuse on
   the next reopen; the in-process `ShaderCache` continues to serve
   from the prior mmap until process restart.
3. **Hot-table refcount stuck.** A `render`-side PSO build that is
   in flight during invalidation holds a borrow on the prior entry;
   `invalidate_by_source_hash` returns the hash in `evicted` but the
   actual `index_` removal waits for the borrow to drop. In editor
   builds this is a serialisation point (the watcher thread blocks
   ≤ one PSO build; bounded by the §9 budget). Under
   `GLIBRE_ALLOC_STRICT=1` a pathological stuck refcount surfaces as
   `Error::OutOfBudget` after a 50 ms timeout; default builds wait.

In every refusal case the prior cache state remains live and
`render`'s PSO bindings are unchanged; SPEC §8.4's "no
half-invalidated state" rule is the operational projection.

## 9. Performance

### 9.1 Lookup wall-time budget (hot path)

| Operation                            | Budget    | Source                                          |
|--------------------------------------|-----------|-------------------------------------------------|
| `ShaderCache::get` hot-table hit     | ~5 µs     | SPEC §9.3 row `ShaderCache (§4.6)`              |
| `ShaderCache::get` warm (cold) load  | <1 ms     | §3.5.1 cold path; manifest bsearch + mmap + Fory decode |
| `ShaderCache::insert` (cooker)       | n/a       | Tooling-only; cook-time budget is out of scope (SPEC §9.2) |
| `invalidate_by_source_hash`          | <100 µs per affected permutation | Unique-lock hold + index walk; bounded by N affected |

The hot-table hit budget is the SPEC §9.3 contract. The 5 µs
absorbs:

- One BLAKE3-keyed `eastl::hash_map` probe (~20 ns on M1).
- One `std::shared_lock` acquire / release pair (~5 ns).
- One `Entry::refcount` atomic increment / decrement pair (~3 ns).
- The remainder is the call-site overhead from `render`'s PSO build
  (~4 µs of inlining / register pressure across the seam).

`ShaderCache`'s own contribution is ~30 ns; the 5 µs SPEC budget is
deliberately loose to absorb compiler / cache-line variance.

### 9.2 Per-context heap cell with eviction

The 24 MiB hot-set ceiling (SPEC §9.4 pool table) decomposes:

| Sub-pool                         | Bound      | Notes                                                 |
|----------------------------------|------------|-------------------------------------------------------|
| `HotTable::index_` (hash-map)    | <0.5 MiB   | `eastl::hash_map<ShaderHash, Entry>` overhead.        |
| `HotTable::lru_` (2Q queues)     | <0.5 MiB   | Two `eastl::list<ShaderHash>` linkages.               |
| Decoded `ShaderArtifact` bodies  | ~23 MiB    | Bytecode + reflection + descriptor layout per entry; ~10 k entries × ~2.3 KiB avg at MVP scale. |
| Mmap'd manifest + CAS pages      | (kernel-pager-tracked, not counted) | mmap'd pages live in the kernel page cache; not allocator-tagged. |

Allocator integration:

- All allocations under `ContextTag::shader` per
  `reviews/decisions/perf-budget.md` Allocator Rules.
- Strict-mode (`GLIBRE_ALLOC_STRICT=1`) returns
  `std::unexpected{core::Error::OutOfBudget}` if an admission would
  push live bytes over 24 MiB (the SPEC §9.4 pool table ceiling for
  the `shader` context; includes the ~0.5 MiB index and LRU
  overhead plus the ~23 MiB decoded-body pool).
- Shipping mode logs a once-per-frame `warn` and silently degrades
  (the new entry is evicted before admission, equivalent to a miss
  the next time the hash is requested; a re-warm follows in the next
  level-stream slot).
- Mmap'd pages do **not** count against the 24 MiB ceiling per
  Allocator Rule §4 (transient kernel-pager memory).

### 9.3 Eviction policy

**2Q-LRU.** Two queues:

- `A1` (FIFO) — newly admitted entries. On eviction pressure, evict
  from the head.
- `Am` (LRU) — entries promoted from `A1` after a second hit. On
  eviction pressure, evict from the head only after `A1` is empty
  (i.e., favour evicting cold-streamed scan entries before hot
  re-used entries).

A hit on an `A1` entry promotes it to `Am`'s tail. A hit on an `Am`
entry moves it to `Am`'s tail. On eviction, the policy picks the
head of `A1` if non-empty, else the head of `Am`. Either way, the
victim must have `refcount == 0`; otherwise the policy advances to
the next candidate (queue stays in FIFO / LRU order; the borrow
holder is the victim's borrower, not its own placeholder).

**Why 2Q over straight LRU.** A cooker walking the entire permutation
enumeration in editor / dev-loop builds streams every artifact through
the cache once; under straight LRU this evicts the steady-state hot
set. 2Q's `A1` admission queue absorbs the scan; the steady set in
`Am` survives. The implementation cost is ~30 LoC over LRU; the
correctness cost is one extra queue's worth of reasoning.

**Why not LFU / ARC.** LFU's recency-blindness misbehaves on
level-stream transitions (the prior level's hot artifacts retain
high frequency counts and resist eviction). ARC's adaptive partition
adds state and a tuning knob the SPEC §9 budget does not need — 2Q's
fixed split is sufficient at MVP scale. Post-MVP may revisit; that
is an `[OPEN]` question (§12).

### 9.4 Cold-start cost

SPEC §9.5: ≤ 50 ms wall-clock to open the cooked `ShaderLibrary` on
M1. The decomposition:

- `mmap(manifest.fory)` — ~1 ms (kernel I/O + page-table setup).
- Fory-decode the manifest header (count, abi hash, sort-order
  validation) — ~5 ms.
- Build the `eastl::vector<ShaderManifestEntry>` from the decoded
  bytes — ~30 ms at 10 k entries.
- Spare — ~14 ms for filesystem variance / first-access page faults.

This is the §9.4 pool table's "cold-start manifest scratch" 4 MiB
transient arena; it drains by phase 9 of frame 0 (per perf-budget.md
Allocator Rule §4).

The hot table is **not** pre-populated at init; it warms lazily on
first `get`. PSO miss cascades during the first level load drive a
~10 k-entry warm in <100 ms wall-clock; this is amortised across the
load screen and not charged against any frame budget.

## 10. Failure Modes

### 10.1 `ShaderCache`-emitted `shader::Error` arms

The cache surface emits five of SPEC §10's enumerators. Restated with
the `ShaderCache`-specific trigger and recovery:

| Enumerator               | Trigger (cache-specific)                                                                                                | Recovery                                                                                       | Severity   |
|--------------------------|------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------|------------|
| **`CacheLookupMiss`**     | `ShaderCache::lookup` finds no manifest entry for the requested `ShaderHash`. **This is the success case in disguise** — the only `Error` arm callers handle non-fatally. | tooling: enqueue compile via `CompilationPipeline`. shipping: refuse bind; `render` falls back to its own missing-PSO policy. | `fallback` |
| **`CacheCorrupt`**        | A CAS file's BLAKE3 self-check fails on cold load (§3.5.1 step 6); the manifest references a hash whose CAS file is absent (§3.7 check 1); the Fory decode raises a record-shape error. | refuse the load of the corrupt entry; surface to the editor / cooker; the cooker re-runs to repopulate. Other entries in the same manifest remain live. | `fatal`    |
| **`CacheIntegrity`**      | `schema_abi_hash` mismatch (§7.2 case 1); `ShaderArtifactRecord.version` outside supported range (§7.2 case 2); manifest-vs-CAS skew detected by §3.7; a `ShaderHash` collision against a non-byte-equal payload during cooker insert. | refuse `open` / refuse `insert`; the in-flight artifact (if any) is dropped; the prior hash continues to resolve. Re-cook required. | `fatal`    |
| **`CacheReadOnlyViolation`** | Shipping `shader.dylib` observes a write attempt (`insert`, `cook`, `invalidate_by_source_hash`, or `compact`) against a `read_only_=true` cache; or a second cooker process fails to acquire the writer lock (§3.6 invariant 3). | refuse the write; abort the offending caller (build-system bug, never user fault). | `fatal`    |
| **`OutOfBudget`** (`core::Error`, not `shader::Error`) | An admission to `HotTable` would push `live_bytes_` over 24 MiB (SPEC §9.4 pool table ceiling) under `GLIBRE_ALLOC_STRICT=1`; or a stuck `Entry::refcount` blocks an eviction past the 50 ms watcher-thread timeout. | strict mode: surface to caller; non-strict mode: log `warn`, evict the new entry pre-admission, return a hot-table miss next time. | `fatal` (strict) / `fallback` (non-strict) |

### 10.2 Refuse semantics

- **Refuse before any in-flight write commits.** §3.6 step 3k's
  atomic-write-with-self-check is the commit point; any failure
  before that point leaves the on-disk store untouched.
- **Refuse after manifest commit triggers re-cook.** A failure
  detected during step 5 or 6 is rare (it implies the
  atomic-write-with-self-check passed but the integrity walker
  disagrees — typically a filesystem corruption or a concurrent
  external mutation). The cooker logs the offending `(ShaderHash,
  producer_label)` pair and asks the asset-pipe to re-run.
- **Never silent retry.** SPEC §10.1 row `refuse` and §10.3 blanket
  rule. The plugin does not re-spawn slangc, does not synthesise a
  best-effort artifact, does not publish a partially-cooked manifest.

### 10.3 Logging

Per `reviews/decisions/error-model.md`:

- Every refusal logs at `warn` (refuse / fallback severities) or
  `error` (fatal severity) with structured fields:
  - `cache_root` — `<library_root>` path.
  - `artifact_hash` — hex `ShaderHash` (32 bytes → 64 chars).
  - `source_hash` — hex `source_hash` from the embedded record (only
    on `CacheCorrupt` / `CacheIntegrity`).
  - `producer_label` — from the embedded record (only on `CacheCorrupt`
    / `CacheIntegrity`).
  - `error_arm` — stable string from `to_string(Error)` (SPEC §5).
- `CacheLookupMiss` is **not logged** at the `ShaderCache` boundary;
  it is the success-in-disguise arm and would flood logs at level-
  stream boundaries. The cooker / editor logs the miss at its layer
  if the miss surprises (a miss for a permutation enumerated in the
  manifest is worth flagging; a miss for one not enumerated is
  expected).

### 10.4 Cross-references

- Closed enum source-of-truth: SPEC §5 (the §10 table tracks the §5
  declaration; both are amended together when a new arm lands).
- Hot-reload refusal projection: SPEC §8.4 (refusal cases 1–4).
- Engine-wide error policy: `reviews/decisions/error-model.md`
  (per-context enums roll into `glibre::Error` variant; logging via
  `glibre::log_error`).
- Severity contract: SPEC §10.1.

## 12. Open Questions

- [OPEN] **2Q vs ARC vs CLOCK-Pro for post-MVP eviction.** The §9.3
  decision is 2Q for MVP. ARC's adaptive partition may pay off for
  post-MVP archives that exceed the 24 MiB hot-set ceiling under
  steady load, but ARC adds state and a tuning knob the MVP budget
  does not need. CLOCK-Pro is a candidate if the implementation cost
  of ARC's "ghost lists" proves prohibitive. Owner: post-MVP
  shader-cache spike (not yet filed).
- [OPEN] **Per-`<aa>/<bb>` shard locks vs single hot-table mutex.**
  §6 picks a single `std::shared_mutex` for the hot table on the
  grounds that contention is reader-dominated and writers are rare.
  A post-MVP archive with multi-thread cooker writers (parallel cook
  per `<aa>/<bb>` shard) may benefit from per-shard locks; the cost
  is the cross-shard atomicity of `live_bytes_`. Owner: same.
- [OPEN] **Cooker-side multi-process advisory lock granularity.**
  §3.6 invariant 3 picks a single `flock(2)` on
  `<library_root>/.cook.lock`. A future asset-pipe orchestration
  layer that runs N cookers in parallel against disjoint
  `<aa>/<bb>` shards could split this into per-shard locks, but
  that requires a manifest-merge step the current cooker does not
  have. Owner: asset-pipe spike (not yet filed).
- [OPEN] **`Library::get` versus `ShaderCache::get` unification.**
  §4 keeps two parallel surfaces because the cooked `Library` is a
  read-only projection while `ShaderCache` is the editor /
  dev-loop's read+write surface. A future refactor could fold them
  by templating on the `read_only` axis; the current split is
  deliberate (smaller link target in shipping, clearer test
  surface). Owner: implementation review.
- [OPEN] **`producer_label` schema discipline.** §3.3 declares
  `producer_label` as `string`, no schema. A drift between cookers
  (slang-1.7 vs slang-1.8) is invisible at the boundary. A future
  enforcement layer would parse the label as `(backend_id,
  backend_version, driver_id, driver_version)` and refuse on
  unrecognised tuples. Owner: post-MVP shader-tooling spike (not
  yet filed).
- [OPEN] **Compaction trigger policy.** §3.8 declares compaction as a
  manual cooker subcommand. An automated trigger (e.g., "compact when
  any `<aa>/<bb>` directory exceeds 16 k entries") would simplify the
  asset-pipe operator's role but adds a policy decision the §1 SRP
  prefers to defer. Owner: asset-pipe spike.
